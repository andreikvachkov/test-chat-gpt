# Запуск на Windows через Docker Desktop и WSL2

В этом варианте PHP, Composer, Node.js и PostgreSQL работают в контейнерах. Устанавливать их в Windows или Ubuntu не нужно. Docker-конфигурация предназначена для локальной разработки.

## 1. Подготовка Windows и WSL

В PowerShell проверьте версию установленного Linux:

```powershell
wsl --list --verbose
```

В колонке VERSION у вашей Ubuntu или другой рабочей системы должно быть `2`. Если там `1`, переключите нужный дистрибутив командой `wsl --set-version Ubuntu 2`, подставив его точное имя.

Установите и запустите Docker Desktop. В настройках:

- General → Use the WSL 2 based engine.
- Resources → WSL Integration → включите ваш Linux-дистрибутив.
- Используйте Linux containers.

Откройте Linux-консоль от обычного пользователя Linux (не `root`) и проверьте:

```bash
docker version
docker compose version
```

Нужен Compose V2 с поддержкой `--wait`. Если клиент не видит сервер, сначала запустите Docker Desktop и проверьте интеграцию с дистрибутивом; отдельный Docker Engine внутри Ubuntu для этого сценария не требуется.

## 2. Размещение файлов

Распакуйте проект **в файловую систему Linux**, например `~/projects/kamali`. Это ускоряет Composer/npm и позволяет нормально отслеживать изменения файлов. Для скачанного в Windows архива можно выполнить из WSL:

```bash
mkdir -p ~/projects
unzip "/mnt/c/Users/ВАШЕ_ИМЯ/Downloads/kamali-docker.zip" -d ~/projects
cd ~/projects/kamali
```

Укажите свой путь к архиву. Если `unzip` не установлен, установите его пакетным менеджером дистрибутива. Для редактирования удобно открывать папку через VS Code с расширением WSL.

## 3. Первый запуск

В папке проекта, из Linux-консоли:

```bash
bash scripts/docker.sh setup
```

Первый запуск загружает образы и собирает расширения PHP, поэтому занимает больше времени. Команда:

1. Создаёт `.env.docker` со случайными ключом приложения и паролем базы; существующий файл сохраняет.
2. Собирает PHP-образ и запускает PostgreSQL с проверкой готовности.
3. Устанавливает Composer/npm зависимости в отдельные Docker volumes.
4. Применяет миграции и добавляет начальный контент, сохраняя последующие редакторские изменения.
5. Собирает Vue, запускает Nginx/PHP-FPM и проверяет HTTP-ответ магазина.

После успешного завершения откройте в браузере Windows адрес `http://localhost:8080`. Панель администратора — `http://localhost:8080/admin`.

Для создания администратора:

```bash
bash scripts/docker.sh admin admin@example.com
```

Укажите нужную почту; команда запросит имя и скрытый пароль. Стандартного административного пароля нет.

По умолчанию каталог пуст. Для тестовых товаров из верстки:

```bash
bash scripts/docker.sh artisan db:seed --class=DemoCatalogSeeder
```

## 4. Ежедневная работа

```bash
# Запуск готовой версии после перезагрузки компьютера
bash scripts/docker.sh up

# Остановка; данные PostgreSQL и зависимости остаются в volumes
bash scripts/docker.sh down

# Состояние и последние журналы
bash scripts/docker.sh status
bash scripts/docker.sh logs app web db

# Любая команда Laravel
bash scripts/docker.sh artisan migrate --force
```

Не добавляйте к `down` параметр `-v`, если нужно сохранить базу. Ключ приложения и пароль хранятся в `.env.docker`; обычный запуск их не меняет. Изменение пароля в файле само по себе не меняет пароль уже созданной роли PostgreSQL.

Исходники и загруженные изображения находятся в папке проекта. Данные базы — в именованном volume `postgres_data`, зависимости — в `vendor` и `node_modules` (с префиксом проекта Compose). Поэтому команды PHP/Composer/npm выполняйте внутри контейнеров, а не через установленные на Windows версии.

## 5. Изменение Vue с быстрым обновлением

После первого `setup`:

```bash
bash scripts/docker.sh dev
```

Сайт открывается по прежнему адресу `http://localhost:8080`; дополнительный сервис Vite использует порт `5173`. Vue-изменения обновляются автоматически. Для перехода обратно к собранной версии:

```bash
bash scripts/docker.sh build
bash scripts/docker.sh up
```

`up` останавливает Vite и удаляет только его служебный файл `public/hot`. Если проект всё же лежит на `/mnt/c` и изменения не замечаются, можно поставить `VITE_USE_POLLING=true` в `.env.docker` и повторить `dev`; хранение в Linux-папке остаётся предпочтительным.

## 6. PostgreSQL и тесты

Из контейнера приложения база доступна как `db:5432`. Внешние программы на Windows/WSL подключаются к `127.0.0.1:5433`; имя базы/пользователь/пароль находятся в вашем `.env.docker`. Порт БД опубликован только на loopback-интерфейсе компьютера.

```bash
bash scripts/docker.sh test
```

Команда использует отдельную базу `kamali_test`; рабочие данные `kamali` не очищаются тестовым набором. В том числе запускаются проверки двух одновременных покупок через независимые подключения к PostgreSQL.

`.env.docker` используется Compose и контейнером приложения. Обычный `.env` сохраняется для другого способа запуска и не перезаписывается. Реальные `.env`-файлы не входят в Git, Docker build context и архив.

## 7. Порты и возможные затруднения

Настройки находятся в `.env.docker`:

| Назначение | Настройка | По умолчанию |
| --- | --- | --- |
| Сайт | `APP_PORT`, соответствующий `APP_URL` | 8080 |
| PostgreSQL с компьютера | `DB_FORWARD_PORT` | 5433 |
| Vite | `VITE_PORT` | 5173 |
| Владелец файлов WSL | `LOCAL_UID`, `LOCAL_GID` | определяются при `init` |

Если порт занят, измените его и повторите `up` или `dev`. Для сайта измените и `APP_URL`, например на `http://localhost:8081`. Внутренние `DB_HOST=db` и `DB_PORT=5432` при этом не меняются.

При ошибках прав проверьте, что проект расположен в домашней папке Linux, а `LOCAL_UID/LOCAL_GID` соответствуют выводу `id -u` и `id -g`. Повторный `setup` назначает владельца только Docker volumes зависимостей; он не меняет владельца всего дерева исходников. Исходные файлы запуска хранятся с переводами строк LF.

Онлайн-оплата, SMS, обмен с 1С и автоматический СДЭК остаются отдельными интеграциями. Письма восстановления в этой конфигурации идут в Laravel log, а не во внешнюю почту.
